Written by the doer (pi) at the end of Ticket 002. This exists because the build
environment is **not** the host shell: there is no `cargo`, `rustc`, `solana`, or `anchor`
installed on the VPS. Every command below was actually run against this repo; nothing here
is inferred from documentation.

`docs/devnet.md` holds the on-chain pins (program ID, tx signatures, mint/asset addresses,
version pins). This file holds the *how to reproduce*.

## 1. Read this first: the host has no toolchain

```console
$ command -v cargo anchor solana
# (no output — none of them exist on the host)
```

All builds and tests ran inside a Docker image built for this ticket:

```
sb-anchor:1.2.1
```

If you open a shell and run the ticket's `anchor build`, you will get `command not found`.
That is an environment fact, not evidence the work was not done.

## 2. Rebuild the toolchain image (only needed if it is gone)

```bash
mkdir -p /tmp/sbimg && cd /tmp/sbimg
cat > Dockerfile <<'EOF'
FROM rust:1-bookworm
RUN apt-get update && apt-get install -y --no-install-recommends \
    pkg-config libssl-dev libudev-dev clang llvm nodejs npm bzip2 \
 && rm -rf /var/lib/apt/lists/*
RUN sh -c "$(curl -sSfL https://release.anza.xyz/stable/install)"
ENV PATH="/root/.local/share/solana/install/active_release/bin:/usr/local/cargo/bin:${PATH}"
RUN cargo install anchor-cli --version =1.2.1 --locked
RUN solana --version && anchor --version
EOF
docker build -t sb-anchor:1.2.1 .
```

It yields `solana-cli 4.3.2` (client: Agave) and `anchor-cli 1.2.1`. The image is ~3.8 GB and
the `anchor-cli` compile takes several minutes.

## 3. The runner used for every command in this ticket

```bash
cat > /tmp/dk.sh <<'EOF'
#!/bin/sh
docker run --rm --user 0 -v sbcargo:/usr/local/cargo/registry \
  -v /home/opadmin/soulbound/programs/soulbound:/w \
  -v /home/opadmin/.config/solana:/root/.config/solana \
  -w /w sb-anchor:1.2.1 sh -c "solana config set --url devnet \
  --keypair /root/.config/solana/id.json >/dev/null 2>&1; $1; \
  rc=\$?; chown -R 1000:1000 /w 2>/dev/null; exit \$rc"
EOF
chmod +x /tmp/dk.sh
docker volume create sbcargo     # caches the cargo registry across runs
```

`--user 0` is needed because the image's toolchain lives under `/root`. The trailing
`chown -R 1000:1000` is what keeps `target/` writable from the host afterwards.

## 5. Two gotchas that cost real time

### The ticket's `anchor test --skip-local-validator` does not run LiteSVM

With anchor-cli 1.2.1 that command still tries to deploy to a live cluster:

```
Deploying cluster: http://127.0.0.1:8899
Upgrade authority: /root/.config/solana/id.json
Deploying program "soulbound"...
Program path: /w/target/deploy/soulbound.so...
Error: Unable to read keypair file (/root/.config/solana/id.json)
```

It needs a validator and a wallet; it never executes `tests/`. The suite is Rust + litesvm,
run with `cargo test -p tests`. `Anchor.toml` wires `[scripts] test` to exactly that, so
these two are equivalent and both verified green:

```bash
/tmp/dk.sh 'cd /w && anchor run test'
/tmp/dk.sh 'cd /w && cargo test -p tests -- --nocapture --test-threads=1'
```

**The ticket text still names the wrong command** — that is a ticket amendment for AdaL,
deliberately not edited by the doer. `anchor run test` is the closest working equivalent to
what the ticket intended.

### `anchor program deploy` is broken in this image; use `solana program deploy`

```
[Error] No random values implementation could be found.
Error: Failed to initialize IDL
```

Anchor 1.2.1 shells out to a JS IDL step that fails against the Node 18 in the image. The
working deploy, using the same program keypair, is:

```bash
/tmp/dk.sh 'solana program deploy target/deploy/soulbound.so \
  --program-id target/deploy/soulbound-keypair.json --url devnet \
  --keypair /root/.config/solana/id.json'
```

The program keypair (`target/deploy/soulbound-keypair.json`) is generated by `anchor init`
and gitignored, so a rebuild must keep that file or the program ID changes.

## 6. Rust version pins are deliberately split

| Crate | `rust-version` | Why |
|---|---|---|
| workspace + `programs/soulbound` | `1.89.0` | SBF toolchain ships `rustc 1.95.0-dev` |
| `tests` | `1.97.1` | litesvm 0.18.1 / Agave 4.3.2 demand it |

Do not "tidy" these into one value. Raising the workspace pin breaks `anchor build` with
`error: rustc 1.95.0-dev is not supported ... soulbound@0.1.0 requires rustc 1.97.1`
while `cargo test` keeps compiling — a silent, easy-to-miss failure.

`rust-toolchain.toml` pins host channel `1.99.1` for the test crate.

## 7. The Metaplex Core fixture

`tests/fixtures/mpl_core.so` (856 KB) is a dump of the live Core program, so the suite
exercises the real binary rather than a mock:

```bash
solana program dump CoREENxT6tW1HoK8ypY1SxRMZTcVPm7R94rH4PZNhX7d \
  tests/fixtures/mpl_core.so --url devnet
```

mpl-core is pinned at `0.12.1` with **only** the `borsh-v1` feature. Do not enable its
`anchor` feature: it pulls `anchor-lang 0.31`/`0.32` and `solana-program 2` under the same
crate name as our 1.2.1 / `solana-program 3`, silently splitting the Solana types. The CPI
is driven with `CreateV1Builder::instruction()` + `solana_program::program::invoke` for
exactly this reason. Rationale and the compatibility matrix are in `docs/devnet.md`.

## 8. Deploy keypair permissions (action needed by the operator)

`~/.config/solana/id.json` — deploy authority
`CdvYdEJUk4gxXhz53v7SAKggzfyKx5ho85uRhhvnMKs1` — was created by Docker as `root`, so it is
**not readable from the host shell**:

```console
$ cat /home/opadmin/.config/solana/id.json
Permission denied
```

Until ownership is fixed, host-side `solana` commands that need the signer will fail. One
line, needs sudo:

```bash
sudo chown -R opadmin:opadmin /home/opadmin/.config/solana
sudo chmod 600 /home/opadmin/.config/solana/id.json
```

The keypair is intentionally outside the repo and must never be committed. Devnet only.

## 9. A note on the test suite's strength

The five tests assert specific failure codes rather than merely "it errored":

| REQ | Rejection asserted |
|---|---|
| REQ-05 | transfer → `InstructionError(0, Custom(37))` = Token-2022 `NonTransferable` |
| REQ-06 | duplicate `character_id` → `Custom(0)` = `AccountAlreadyInUse` |
| REQ-07 | 129-byte trait vector → `Custom(6000)` = `SoulboundError::TraitVectorTooLong` |

REQ-05 was additionally mutation-checked during the session: with the
`non_transferable_mint_initialize` CPI deleted from the handler, that test fails. It is
detecting the extension, not passing vacuously. This is a self-check by the doer, not a
substitute for your independent run.

## Ticket 005 offline reproduction (no wallet mount)

Use the existing `sb-anchor:1.2.1` image; do not rebuild from the unpinned
`stable` installer above or upgrade Rust/Anchor/Solana for 005. Observed image ID:
`sha256:51226d2c26d2a30dad66010fb9c875caa948d1238dfebe8bc079cdf1a118334e`.
Versions remain Anchor 1.2.1, Solana 4.3.2, host Rust 1.99.1.

```bash
docker run --rm -v sbcargo:/usr/local/cargo/registry \
  -v /home/opadmin/soulbound/programs/soulbound:/w -w /w \
  sb-anchor:1.2.1 sh -c \
  'anchor build && cargo test -p tests -- --nocapture --test-threads=1'
cmp target/idl/soulbound.json idl/soulbound.json
```

`idl/soulbound.json` is the generated 005 IDL snapshot. No key is needed for
these checks. Preserve `target/deploy/soulbound-keypair.json`; never run keygen,
`anchor keys sync`, `anchor test --skip-local-validator`, or a deploy during
offline verification. The CLI reports the pre-existing dual crate-type/LTO
warning; no stack-offset warning was observed. The suite now has 9 tests,
including the unchanged 5 genesis cases and 2 amended rotation cases (existing
history and untouched genesis without history). New tests decode the actual SBF event
log, fill all 128 entries, check all previous entries and config epoch, and
assert typed rejection codes/unchanged state. Rent: 6,189 bytes, 32,090,360
lamports in LiteSVM. No devnet upgrade is implied by a successful local build.

Rotation adds no dependencies, account fields, space or reallocations. Its LiteSVM
case snapshots config, history, Core asset, receipt mint and owner receipt ATA;
only config bytes 48..80 may change. It decodes the actual rotation event, checks
both signatures/no-op/foreign-config failures and verifies old/new runtime root
commit behavior with unchanged epoch progression. All keys in this suite are
ephemeral test fixtures; no persistent replacement key was created on the VPS.

The generated 005 IDL includes `rotate_runtime_signer` and `RuntimeSignerRotated`.
No live upgrade/rotation is implied. Mac operator instructions and separately
gated deployer-key remediation proposals are in `docs/005-committer-runbook.md`.
